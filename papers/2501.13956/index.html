    01

    問題：為什麼靜態 RAG 不夠用

    一般的 AI 查資料，像是在翻一本印好的百科全書，內容不會變。可是你的生活每天都在變：你換了學校、交了新朋友、喜歡的東西也會變。

    Zep 給 AI 一本會自己更新的筆記本，而且每一條都記著「從什麼時候開始是真的、到什麼時候不再是真的」。

    LLM agent 受限於上下文視窗大小、上下文的有效利用、以及預訓練知識。RAG 用資訊檢索補上外部知識，但作者指出現有 RAG 多半假設語料是靜態的：文件放進去之後很少改。

    Agent 的記憶不是這樣。它要處理持續演變的資料：使用者的對話、相關的商業資料、世界資訊。這些內容塞不進上下文視窗，又會隨時間改變，所以需要新的記憶架構。Zep 的答案是一個帶時間資訊的動態知識圖譜，引擎叫 Graphiti。

    問題設定是「agent memory 作為一個可服務化的層」，而不只是單一演算法。作者把關注點放在三件事：準確度、延遲、可擴展性，因為 Zep 是正式上線的產品（§1）。

    和學術型記憶論文的差別值得注意：主要比較對象是 MemGPT 在 DMR 上的成績，再加上 LongMemEval 對全文上下文（full-context）基線。論文沒有和其他記憶系統在 LongMemEval 上正面比較（見 10、12）。

    原文要點 原文 Abstract

    Zep 是給 AI agent 用的記憶層服務，在 DMR 上勝過當時最先進的 MemGPT（94.8% vs 93.4%）。核心元件 Graphiti 是具時間感知的知識圖譜引擎，能同時整合非結構化的對話資料與結構化的商業資料，並保留歷史關係。在更困難的 LongMemEval 上，準確度最多提升 18.5%，回應延遲降低 90%。

    自我檢測
    作者認為現有 RAG 對 agent 記憶不適用的關鍵假設是什麼？

    語料大致是靜態的。Agent 記憶的資料（對話、商業資料）持續變動，而且事實本身有「有效期間」。

    摘要裡的「18.5%」是跟誰比？

    跟 LongMemEval 上的 full-context 基線比（把整段約 115k tokens 的對話直接塞進上下文），用 gpt-4o。不是跟其他記憶系統比。

    02

    三層知識圖譜

    圖的定義與三個子圖原文 §2
    \[ \mathcal{G} = (\mathcal{N}, \mathcal{E}, \phi), \qquad \phi : \mathcal{E} \to \mathcal{N} \times \mathcal{N} \] \[ \mathcal{E}_e \subseteq \phi^*(\mathcal{N}_e \times \mathcal{N}_s), \quad \mathcal{E}_s \subseteq \phi^*(\mathcal{N}_s \times \mathcal{N}_s), \quad \mathcal{E}_c \subseteq \phi^*(\mathcal{N}_c \times \mathcal{N}_s) \]
    子圖節點邊
    Episode 子圖 \(\mathcal{G}_e\)Episode：原始輸入（訊息、文字或 JSON），是不失真（non-lossy）的資料存放處Episodic edge：episode → 它提到的實體
    語意實體子圖 \(\mathcal{G}_s\)Entity：從 episode 擷取、並與既有實體合併後的實體Entity edge（semantic edge）：實體之間的關係，也就是「事實」
    社群子圖 \(\mathcal{G}_c\)Community：高度連結的實體群，帶高層摘要Community edge：社群 → 它的成員實體

    想像一本有三層的剪貼簿。第一層把你說過的每句話原封不動貼上去。第二層畫一張人物關係圖：誰是誰、誰喜歡什麼。第三層把關係很近的人圈成一群，寫一句話介紹這一群。

    三層由下往上越來越抽象：原始對話 → 實體與事實 → 社群摘要。保留最底層的原始資料很重要，因為上面兩層都是 LLM 擷取出來的，可能出錯；有原文就能回頭查證。

    作者把這對應到心理學的兩種記憶：情節記憶（episodic memory，記得某件事發生過）和語意記憶（semantic memory，記得概念之間的關聯）。

    設計來源都有明確引用：episodic／semantic 分離取自 AriGraph [9]，社群節點取自 GraphRAG [4]，整體階層延伸自階層式 RAG [10][11]（§2）。新意主要在兩處：雙時間軸（03、05），以及社群的增量更新（06）。

    符號提醒 導讀補充：\(\phi^*\) 原文沒有定義，從上下文看是「端點落在該節點對集合內的邊」。另外 §3 的搜尋函數用的是另一個字形 \(\varphi\)，不要和這裡的關聯函數 \(\phi\) 混在一起。

    Episode 與 semantic edge 之間維護雙向索引，可以從事實追回出處，也能從 episode 找到相關事實。但原文明說這個功能沒有在實驗中檢驗（§2.1）。

    自我檢測
    為什麼要保留 episode 這層原始資料？

    它是不失真的資料存放處：實體和事實都是 LLM 擷取的，可能有錯或遺漏；保留原文才能引用、查證、重新擷取。

    三種邊分別連接哪些節點？

    Episodic edge：episode → 實體。Entity edge：實體 → 實體。Community edge：社群 → 實體。

    03

    Episode 與雙時間軸

    兩條時間軸、四個時間戳原文 §2.1、§2.2.3
    \[ T:\ \text{chronological order of events}, \qquad T':\ \text{transactional order of ingestion} \] \[ t'_{\text{created}},\ t'_{\text{expired}} \in T', \qquad t_{\text{valid}},\ t_{\text{invalid}} \in T \]
    符號意思（原文）
    \(t_{\text{ref}}\)訊息的參考時間戳，也就是訊息送出的時間。用來把「下週四」「兩週前」「去年夏天」這類相對或部分日期換成絕對時間
    \(T\)事件時間軸：事情在真實世界發生的先後
    \(T'\)交易時間軸：Zep 擷取資料的先後，作用類似資料庫稽核紀錄
    \(t'_{\text{created}}, t'_{\text{expired}}\)事實在系統中被建立、被判定失效的時間
    \(t_{\text{valid}}, t_{\text{invalid}}\)事實在真實世界中成立的期間

    每張貼紙上要寫兩種日期。一種是「這件事是什麼時候發生的」，另一種是「我是什麼時候知道這件事的」。你今天才聽說小明上個月搬家了，那搬家的日期是上個月，你知道的日期是今天。

    Episode 有三種：訊息（message）、文字、JSON。論文的實驗只用訊息。每則訊息帶著說話者和送出時間 \(t_{\text{ref}}\)。

    雙時間模型（bi-temporal model）把兩件事分開：

    • 事實在真實世界什麼時候成立（\(T\) 軸）。
    • 系統什麼時候知道這件事（\(T'\) 軸）。

    分開之後才能回答「三月時使用者在哪工作」和「系統在三月一號那天以為使用者在哪工作」這兩個不同的問題。05 的互動時間軸可以實際操作。

    雙時間模型在資料庫領域是成熟概念（valid time vs. transaction time）導讀補充。原文宣稱把它用在 LLM 建構的知識圖譜是「新的進展」，也是 Zep 和先前圖譜式 RAG 最大的差異（§2.1）。

    值得追問：實驗中有沒有用到 \(T'\)？§3 的 Constructor 只回傳事實與 \(t_{\text{valid}}, t_{\text{invalid}}\)，沒有提到 \(t'\) 欄位，所以 \(T'\) 在論文實驗裡主要是稽核用途，沒有被評估 導讀補充。

    自我檢測
    \(t_{\text{valid}}\) 和 \(t'_{\text{created}}\) 有什麼不同？

    前者在事件時間軸 \(T\) 上，表示事實開始成立的時間；後者在交易時間軸 \(T'\) 上，表示 Zep 寫入這筆事實的時間。

    沒有 \(t_{\text{ref}}\) 的話，哪類資訊會處理不了？

    相對時間，例如「兩週前」「下週四」。必須知道訊息是何時說的，才能換算成絕對日期。

    04

    實體擷取與實體解析

    每則訊息進來後的實體處理流程 原文 §2.2.1、附錄 6.1.1–6.1.2
    步驟做法
    1. 擷取LLM 讀「目前訊息＋前 \(n\) 則訊息」做命名實體辨識。\(n = 4\)，也就是兩輪完整對話。說話者一律抽成實體
    2. 反思受 Reflexion [12] 啟發的反思步驟，降低幻覺、提高擷取覆蓋率
    3. 摘要為每個實體產生摘要，供後續解析與檢索
    4. 找候選實體名稱嵌入 1024 維向量，用餘弦相似度找相近的既有實體；另外對既有實體的名稱與摘要做全文搜尋
    5. 解析候選實體＋episode 上下文交給 LLM 判斷是否重複；重複就合併，並產生更新後的名稱與摘要
    6. 寫入用預先定義的 Cypher 查詢寫進圖資料庫，而不是讓 LLM 產生查詢，以維持 schema 一致、減少幻覺
    擷取提示詞的規則 原文 附錄 6.1.1
    • 永遠先把說話者抽成第一個節點（冒號前的部分）。
    • 不要為關係或動作建立節點。
    • 不要為日期、時間、年份建立節點，這些之後會放到邊上。
    • 節點名稱盡量明確，使用全名。

    第 6 條規則在 PDF 中截斷於 "DO NOT extract entities mentioned only"，原文缺字。

    小幫手讀你說的話，把裡面的人、地方、東西圈出來。然後它會檢查：「這個『小明』是不是我之前認識的那個『王小明』？」是的話就把兩張名片合成一張，不會出現兩個小明。

    實體解析（entity resolution）解決「同一個東西有好多名字」的問題，例如「媽媽」「我媽」「林美玲」。做法是先用兩種搜尋（向量相似度與關鍵字）找候選，再請 LLM 下最後判斷。

    寫入資料庫用固定的 Cypher 模板而不讓 LLM 自由寫查詢，是很實務的選擇：LLM 只負責「理解」，結構化的寫入交給確定性的程式。

    每則訊息要經過實體擷取、反思、實體解析等多個 LLM 步驟，事實那邊還有擷取、去重、時間擷取、失效判斷（見 05）。實驗用 gpt-4o-mini 建圖，但建圖成本與耗時完全沒有報告，Table 2 的延遲只算檢索與回答 導讀補充。

    1024 維應該對應實驗用的 BGE-m3 embedding（§4.1），但原文沒有把兩者直接連起來。擷取品質（實體召回率、解析正確率）也沒有獨立評估。

    自我檢測
    為什麼不讓 LLM 直接寫 Cypher 查詢？

    原文的理由：確保 schema 格式一致、降低幻覺的可能。

    擷取時為什麼要看前 4 則訊息？

    提供上下文給命名實體辨識，例如代名詞「他」指誰。4 則剛好是兩輪完整對話。

    05

    事實、時間擷取與邊的失效

    事實是實體之間的邊，帶一個全大寫的關係類型（例如 LOVES、WORKS_FOR）和一句詳細描述（附錄 6.1.3）。同一個事實可以在不同實體對之間重複擷取，藉此表示牽涉多個實體的事實，原文稱為超邊（hyper-edge）的實作 原文 §2.2.2。

    去重：新事實先嵌入，再用混合搜尋找重複，但只在同一對實體之間的邊裡找。這樣既避免把不同實體間的相似事實誤合併，也大幅縮小搜尋範圍 原文 §2.2.2。

    邊的失效規則原文 §2.2.3（文字敘述，本頁寫成式子）
    \[ \text{if } e_{\text{new}} \text{ contradicts } e_{\text{old}} \text{ and they overlap in time:}\qquad t_{\text{invalid}}(e_{\text{old}}) \leftarrow t_{\text{valid}}(e_{\text{new}}) \]

    由 LLM 比對新邊與語意相關的既有邊，找出時間上重疊的矛盾。依交易時間軸 \(T'\)，Graphiti 一律優先採信新資訊。舊邊不刪除，只是設定失效時間，所以現況與歷史都保留。

    時間擷取提示詞的規則（節錄） 原文 附錄 6.1.5
    • 只擷取屬於該事實本身的時間；不要從相關事件推論日期。
    • 相對時間（「10 年前」「2 分鐘前」）以參考時間戳換算。
    • 事實以現在式描述時，\(t_{\text{valid}}\) 用參考時間戳。
    • 只有日期沒有時刻，用當天 00:00:00；只有年份，用該年 1 月 1 日 00:00:00。
    • 不是「持續一段期間」的關係，只設 valid_at。日期用 ISO 8601，一律帶時區（沒提到就用 Z）。

    你本來記得「哥哥在 A 公司上班」。後來哥哥說「我兩週前換到 B 公司了」。Zep 不會把 A 公司那張貼紙撕掉，而是在上面寫「到 2 月 20 日為止」。這樣它既知道哥哥現在在哪，也記得哥哥以前在哪。

    這是 Zep 和「直接覆蓋舊資料」最大的不同：不刪除，只標記失效時間。好處是能回答歷史問題（「他去年在哪工作？」），也能讓 LLM 看到變化的脈絡。

    時間換算全靠 LLM 依提示詞規則完成。規則寫得很細，例如只有年份就取 1 月 1 日，就是為了讓結果一致、可預期。

    幾個值得追問的地方 導讀補充：

    • 規則「現在式取參考時間」會把\(t_{\text{valid}}\)設成「第一次被提到的日子」而不是真正開始的日子，上面的例子就是這樣。這會影響 temporal-reasoning 題的正確性。
    • 失效只處理「時間重疊的矛盾」，判斷交給 LLM。誤判會讓仍然成立的事實被標成失效，原文沒有評估失效判斷的準確率。
    • 「依 \(T'\) 優先採信新資訊」代表較晚才被提到的舊事件也會壓過先前資訊。例如使用者回憶往事時，可能誤觸失效。
    • 和上一篇 FadeMem 對照：FadeMem 讓矛盾的舊記憶強度衰減後刪除；Zep 永不刪除，只設失效時間。前者省空間，後者保留歷史。
    自我檢測
    新事實與舊事實矛盾時，舊事實的哪個欄位會被改？改成什麼？

    \(t_{\text{invalid}}\)，改成新事實的 \(t_{\text{valid}}\)。舊事實本身不會被刪除。

    為什麼事實去重只在同一對實體之間的邊裡搜尋？

    避免把不同實體之間相似的事實誤合併，同時縮小搜尋空間、降低計算量。

    使用者說「我 2019 年搬到台中」，\(t_{\text{valid}}\) 會是什麼？

    依附錄 6.1.5 規則 8，只有年份時取 2019-01-01T00:00:00Z。

    06

    社群：增量式的標籤傳播

    和 GraphRAG 的差異 原文 §2.3
    面向GraphRAG [4]Zep
    分群演算法Leiden [14]標籤傳播（label propagation）[13]
    新資料進來（原文未描述）新實體加入鄰居中多數所屬的社群，再更新社群摘要；仍需定期整體重算
    社群摘要map-reduce 式迭代摘要同樣做法
    檢索方式map-reduce差異很大：從摘要產生含關鍵詞的社群名稱，嵌入後做餘弦搜尋

    新同學轉進班上，要決定他加入哪個小團體。最簡單的方法：看他最常跟誰玩，那些朋友大多在哪一組，他就加入哪一組。過一陣子老師再重新分一次組，因為大家的朋友會變。

    選標籤傳播而不是 Leiden，原因是它很容易做增量更新：新節點只要看鄰居的社群標籤，取多數，就是標籤傳播的一個遞迴步驟。這比每次整張圖重新分群便宜很多，降低延遲與 LLM 摘要成本。代價是增量結果會逐漸偏離完整重算的結果，所以仍需定期刷新。

    這是典型的「近似換效率」取捨。原文沒有量化偏離程度，也沒說刷新頻率 導讀補充。

    更重要的是：§3 的 context 範本只有 FACTS 與 ENTITIES，§4 也說實驗取的是「邊（事實）與實體節點」。從這兩處看，社群很可能沒有用在實驗中，所以社群設計的效果在論文裡沒有證據支持 導讀補充。原文 §4 也承認實驗只用到系統搜尋功能的一部分。

    原文提到社群搜尋方式和 LightRAG [17] 的 high-level key 搜尋相似，兩者是各自獨立發展的。

    自我檢測
    Zep 為什麼選標籤傳播而不是 Leiden？

    標籤傳播有直接的動態延伸：新節點只要依鄰居多數決定社群，可以延後整體重算，降低延遲與 LLM 推論成本。

    你問 AI 一個問題，它要先去筆記本找答案。它用三種找法：找意思很像的、找字一樣的、找跟最近聊到的東西有關係的。找到一大堆後挑出最重要的幾條，整理成一張小抄交給 AI。

    這是常見的「高召回搜尋＋高精確重排」兩段式設計。三種搜尋互補：BM25 抓得到專有名詞，向量搜尋抓得到換句話說，BFS 抓得到「沒提到但有關聯」的東西。最後組成的小抄平均只有約 1.6k tokens（Table 2），而不是整段 115k tokens 的對話。

    符號提醒：§3 的 \(\alpha, \beta\) 是查詢與上下文字串，\(\rho\) 是重排器，和其他論文的常見用法不同 導讀補充。

    實驗具體用了哪些搜尋與重排的組合，原文沒有寫明。§4.1 只說重排與嵌入都用 BGE-m3 模型，§4 說實驗只示範了部分搜尋功能。BFS 是否啟用、種子怎麼選，都不清楚，因此無法判斷哪個元件貢獻了 LongMemEval 的提升 導讀補充。

    自我檢測
    三種搜尋各自捕捉什麼樣的相似性？

    全文搜尋（BM25）：字詞；餘弦：語意；BFS：情境，也就是在圖上距離近、常在相似對話中一起出現。

    Constructor 對每條事實輸出什麼？

    事實文字與它的 \(t_{\text{valid}}\)、\(t_{\text{invalid}}\)，也就是有效日期範圍。

    批判性閱讀

    以下是本頁的評論 導讀補充，依據都在前面各節。

    優點

    • 雙時間模型讓「事實何時成立」與「系統何時得知」分開，是很實用的設計，對 knowledge-update 與 temporal-reasoning 類問題有直接幫助。
    • 工程細節透明：公開提示詞、時間換算規則，以及 Cypher 模板這類降低幻覺的作法。
    • 同時報告延遲與上下文長度，而不只看準確度。作者也坦白指出 DMR 的不足與自己表現退步的題型。

    疑問

    • 利益衝突與重現性：作者全來自 Zep 公司，評測的是自家商業服務；v1 時實驗 notebook 尚未公開。
    • 基線太少：LongMemEval 只對 full-context；沒有一般 RAG、Mem0 或其他圖譜式 RAG。
    • 沒有消融：社群、BFS、重排器、雙時間欄位各自的貢獻都無法得知；社群甚至可能沒用在實驗中。
    • 成本只算一半：延遲只計檢索與回答，建圖時每則訊息多次 LLM 呼叫的成本與耗時沒有報告。
    • 擷取品質沒有評估：實體解析、事實去重、時間擷取、失效判斷都靠 LLM，錯誤會累積在圖中，但沒有任何中間環節的準確率。
    • 數字細節：Delta 的分母不一致、18.5% 應為 18.3%、檢索量 10 與 20 的說法不一致、兩列數字完全相同。
    • 統計：沒有重複執行、信賴區間或顯著性檢定。
    • 只增不減：圖譜不失真、永不刪除，長期的儲存與檢索成本如何成長沒有討論。

    可以延伸的方向

    • 補上「同樣嵌入模型的切塊向量檢索」基線，分離圖結構本身的價值。
    • 評估擷取管線每一步的準確率，特別是時間擷取與失效判斷。
    • 結合 FadeMem 一類的遺忘或歸檔機制，處理圖譜無限成長的問題。

    Hyper-edge：連接兩個以上節點的邊。Zep 以在多個實體對之間重複同一事實來實作。
    Cypher
    Neo4j 等圖資料庫使用的查詢語言。
    標籤傳播
    Label propagation：每個節點反覆採用鄰居中多數的標籤，直到收斂的分群演算法。
    BM25
    Okapi BM25：經典的關鍵字全文檢索排序函數。
    RRF / MMR
    Reciprocal Rank Fusion 合併多個排序結果；Maximal Marginal Relevance 在相關性與多樣性間取捨。
    Cross-encoder
    把查詢和候選一起輸入模型打分的重排器，準但慢。
    IQR
    四分位距，第 75 與第 25 百分位數之差，用來描述延遲的離散程度。
