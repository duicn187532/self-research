    01

    核心主張：分析單位從「記憶」換成「持久狀態」

    操作型定義 原文 §2.1

    Always-on agent 是「在時間 \(t\) 的策略依賴 \(t\) 之前累積、且超出當前提示與任務實例的狀態」的 agent。關鍵是持久，不是真的 24 小時在跑：一天跑一次、被事件喚醒、只在使用者開 session 時啟動，只要行動受到跨次呼叫的持久狀態影響，都算。反過來，一直在跑但每次請求都重置狀態的，是 episodic agent。

    判定條件有三：(1) 跨 session 或重啟的持久身分；(2) agent 自己擁有、可變、持久的狀態；(3) 能把這些狀態用在之後的行動。若狀態有後果，就產生第四項義務：時間問責（temporal accountability），能記錄知道什麼、何時知道、為何行動，以及事後發現被污染時如何找出並修復。前三項用來分類，第四項是現有系統常做不到的。

    以前的 AI 小幫手像金魚，每次聊完就忘光，所以它犯的錯也不會留到明天。現在的小幫手會記得事情，還會根據記得的事情自己去做事。

    這篇論文說：既然它會記得，我們就要管好它記得的東西。哪些可以記？誰說它可以這樣做？記錯了能不能改？做錯了能不能還原？

    作者的論點是：一旦保留下來的狀態可以授權未來的行動，「過去」就不再無關，單一 episode 的安全論證就不成立了（§1）。例子：一個儲存的偏好會默默決定工具呼叫的預設參數；一個快取的憑證在使用者想讓它失效之後仍能存取資源；幾個月前寫的摘要因為檢索分數高，壓過新的證據。

    所以作者把分析單位從「記憶」擴大成持久狀態：除了可檢索的記憶，還包括任務帳本、權限與同意、工具與憑證、出處與稽核紀錄、共享狀態、觸發條件，以及已經發生在外部世界的副作用。

    四項宣稱的貢獻（§1）：(1) 定義與六個診斷軸；(2) 十個階段的生命週期與五個不變量；(3) 以 435 篇編碼語料庫支撐的覆蓋地圖；(4) 評測協議 AOEP 與試點 AOEP-v0。

    作者也處理了一個合理的反駁（§2.1）：治理稀少會不會是理性取捨，因為多數狀態本來就可拋棄？作者的主張是條件式的：只要持久狀態既被保留又有後果，缺少治理就是沒有辯護的設計選擇；真正短暫的狀態不在此列。這個條件式寫法讓論點比較難被一般性反駁，但也代表它的力度取決於「有後果的持久狀態」在實務上有多常見，作者用 §3、§5、§6、§8 的證據來支持。

    原文要點 原文 Abstract

    作者把 always-on agent 視為持久狀態系統，用六個診斷軸（authority、scope、mutability、provenance、recoverability、actionability）與一個生命週期（寫入、驗證、組織、檢索、行動、更新、遺忘、稽核、有時回滾）閱讀文獻。在 435 篇編碼語料庫中（視為有範圍的地圖而非完整普查），文獻較集中於累積與取回狀態，較少處理治理、恢復或放棄狀態。作者因此提出 AOEP-v0，評分狀態變更與恢復義務，而不只看答案品質。

    自我檢測
    一個 24 小時運行、但每個請求都重置狀態的客服機器人，算 always-on 嗎？

    不算。定義的關鍵是持久狀態會影響之後的行動，不是連續執行。它是 episodic agent。

    「時間問責」為什麼不能化約成檢索品質？

    完美取回一個事實，仍無法回答它是否仍被授權、範圍是否涵蓋這次請求、若它是被污染的，哪些過去的行動需要撤銷。這些需要額外的欄位與操作。

    每一張記憶紙條都要回答六個問題：誰說可以照著做？可以用在誰身上？可以改嗎？從哪裡來的？做錯了能復原嗎？它只是一句話，還是一個會真的去做事的指令？

    六個軸不是互相獨立的：出處常常是權威的證據；範圍限制權威；可行動性決定權威與可恢復性要多嚴格；可恢復性依賴出處被保存下來（§2.3）。例如一個有毒的「技能」比一個有毒的「事實」危險得多，因為呼叫技能會在世界上產生工具後果。

    語料的偏斜：可變性（160）與出處（153）最常見，權威（72）最少。作者的解讀是，文獻最關注失敗是「內部、可修正」的軸，最少關注失敗會「授權一個無法收回的行動」的軸。

    認知架構的血緣（§2.4）：Tulving 的情節／語意記憶區分撐起 provenance 軸；互補學習系統（快速海馬迴、慢速新皮質）是 mutability 軸與可塑性－穩定性張力的祖先；Baddeley 的 episodic buffer 對應 scope；ACT-R 的「宣告性 chunk 可取用」與「程序規則依效用觸發」對應 authority 的「持有 vs 被授權使用」，不過作者也說效用是行動選擇偏好而不是授權，authority 軸真正的根據在能力式安全與存取控制。

    作者的關鍵論斷：Soar、ACT-R 的記憶類型邊界由封閉的架構強制，LLM agent 的記憶類型只是同一個儲存庫裡的文字條目加標籤，所以那份隔離必須靠治理重建。CoALA 繼承了分類，卻沒有繼承強制機制。

    小提醒 導讀補充：scope 與 actionability 的語料數在正文中沒有報告，只說 mutability 最多、authority 最少。

    自我檢測
    為什麼 actionability 會決定其他軸要求多嚴？

    錯用的後果隨類型放大。一條建議性的教訓錯了會溫和退化；一個可執行的承諾（例如會付款的技能）錯了會在外部世界造成不可逆的後果，所以需要更強的權威、出處與可恢復性保證。

    AI 記得的東西分三種。第一種是它記住的事情本身。第二種是貼在每件事情上的標籤：誰說的、能用在哪、能不能改、能不能撤回。第三種是它已經在外面做過的事，例如寄出去的信、付出去的錢，這些收不回來，只能記得是哪張紙條讓它這樣做的。

    作者的主要分類修正是：治理不是另一種記憶類型，而是決定任何記住的物件能不能行動的那一層（§3.2）。所以 policy、permission、provenance、deletion handle 不該跟「事實」「偏好」並列，而是附在每個物件上的外殼欄位；副作用則根本不是內部狀態，而是必須能追溯回內部狀態的外部後果。

    各類型也不獨立，而是有衍生順序：情節 → 事實與偏好、成功的情節 → 技能、未完成的情節 → 任務帳本；任何一種都可能被共享、觸發、動用憑證，最後產生副作用。上游壞了，下游跟著壞（§3.4）。

    刪除為何最難（§3.4）：對一個語意事實的遺忘請求，必須沿整條衍生鏈傳播：抽出它的情節、吸收它的摘要與嵌入、以它為條件的技能、其他主體持有的共享副本，以及它授權過的外部副作用。而讓衍生鏈可稽核的不可變出處帳本，同時讓刪除更難兌現，問責與抹除互相衝突，作者說語料還沒有解決這個張力。

    生命週期與五個不變量

    十個階段分成兩段弧 原文 §4、Figure 5。前向弧：observe → write → validate → organize → retrieve → act，把環境訊號帶到行動。回返弧：update → forget → audit → rollback，在行動的後果揭曉後，讓狀態與現實和解。可塑性主要在 write 與 update；穩定性由 validate、audit、forget、rollback 維持。

    十個轉換的定義依原文 §4.1；外送地址的情境、記錄編號與欄位值是示意 導讀補充。

    一張記憶紙條的一生：看到、寫下、檢查能不能信、整理歸檔、需要時拿出來、照著做事；後來發現有變就改、被要求就丟掉、事後查是哪張紙條害的、做錯了就還原。大家都很會前半段，後半段幾乎沒人做。

    和一般記憶管線比，這個框架多了兩個地方：validate 階段與回返弧（§4）。在治理良好的系統裡，write 先寫進隔離層，validate 檢查權威仍有效、出處可信才升到 live；act 要在行動上蓋章記下 handle \(r\)；forget 是 tombstone 加傳播；rollback 用 \(r\) 回復決策與副作用。

    語料的形狀就是論點：retrieve 269、write 200，rollback 只有 27。回返弧上的三個不變量（刪除傳播、回滾可追溯、出處保存的後半）偏偏都依賴最少被研究的階段。

    回滾可追溯跨在兩段弧之間：handle 在前向弧的 act 設定，在回返弧的 rollback 使用。一個只把 act 裝上儀器、卻沒建回返弧的系統，記下了 handle 卻沒地方用（§4.1.1）。反過來，沒在 act 記 handle 的系統，即使想回滾也不可能。

    OS 抽象（MemGPT、MemoryOS、sleep-time consolidation）提供分層、排程、檢查點等機制，但它們治理的是資源正確性，不是狀態正確性：例如可能在記錄被使用前就把它逐出，或因為存取頻繁而升級一筆低權威記錄（§4.4）。

    關於 27 這個數字，作者自己的提醒（附錄 A.6）：它合計了三種機制上不同的回滾（內部狀態、工作流程、外部副作用），對最簡單的一類偏寬，對最難的外部副作用回滾幾乎一定高估。

    自我檢測
    為什麼「衰減式遺忘」不滿足刪除傳播？

    被降權的記錄仍然存在、在適當查詢下仍可被取回；而且衍生的摘要與嵌入不受影響。原文 §4.3.2 稱之為「刪除只是檢索編輯，不是抹除」。

    五個不變量中，哪兩個完全或主要依賴回返弧？

    刪除傳播（在 forget 建立、在 audit 驗證）與回滾可追溯（在 rollback 使用）。出處保存也有一半依賴回返弧的 update 與 audit。

    最有意思的是 Table 18 中三個原始儲存系統分數完全相同（7/15）：不管是看最近、全部放進上下文、還是向量檢索，都通過能靠語意回想推出的義務（某值是否被刪、某指令是否被隔離），都在需要「維護治理狀態」的義務上失敗（回報 epoch、擋下任務、浮出衝突、記錄回滾）。資訊不是不在上下文裡，而是文字儲存根本沒有欄位放 epoch、隔離狀態、衝突紀錄、回滾帳本。

    優點

    • 分析單位的轉換很有說服力：把權限、憑證、任務帳本、副作用與記憶放進同一個框架，記憶綜述確實沒有這樣做。

    • 對自己引用的治理機制保持懷疑，承認多數是未經生產驗證的預印本。

    疑問

    • 框架自我驗證的風險：六個評測壓力源由作者自己的軸與生命週期推導，再用來證明現有評測不足；這個循環讓「現有評測沒覆蓋」幾乎是定義上成立的。

    • 語料年代分布：421 篇有年份的作品中 252 篇是 2026 年，治理相關的大多是未經同行審查的預印本。
    • AOEP 試點規模：九種故障模式、15 個義務、3B–8B 的本地讀取模型；上界 reducer 依同一套規則實作；關鍵消融沒有跑。作者都承認，但結論的強度應據此調低。

    • 跑作者點名的那個消融：給 Mem0 類抽取式記憶加上最小治理外殼（epoch、刪除帳本、信任層級），看能補回多少義務分數。

    不是全領域普查；不同詞彙的治理研究可能沒被搜到（附錄 A.7）。
    評語
    充分支持 限於「這份語料、方向性的差距」：269 對約 27 是數量級的差距，標籤誤差放大數倍也不會反轉。精確數字則只是估計。
    主張二：authority 是最少被觸及的狀態軸。
    支持證據
    authority 72，對 recoverability 112、mutability 160（§2.3）。
    其他解釋
    狀態軸的編碼一致性 κ = 0.44，72 對 112 不到兩倍的差距可能受編碼誤差影響。
    直接測到嗎
    直接計數。
    未測的邊界
    scope 與 actionability 的計數正文沒有報告，所以「最少」只是相對於有報告的軸。
    評語
    部分支持 方向可能成立，但與次少的軸差距不大，排名不穩。
    主張三：現有評測對六個壓力源是乾淨的分割，沒有評測同時涵蓋真實行動、隱私邊界與恢復（§7.7）。
    支持證據
    Table 13 對代表性評測的覆蓋編碼。
    其他解釋
    六個壓力源是從作者自己的軸與生命週期推導出來的，用它來說現有評測不足，有一定程度的循環。
    直接測到嗎
    直接編碼了所列評測，但 Table 13 只對三個家族逐篇編碼。
    未測的邊界
    長上下文／RAG 與個人化家族只在家族層級描述。
    評語
    部分支持 對所列評測成立；推到「整個評測文獻」需要更完整的逐篇編碼。
    主張四：AOEP 能區分有治理欄位的儲存與只有文字的儲存（§9.4）。
    支持證據
    Table 18：reducer 15/15；三個純文字儲存系統都是 7/15；抽取式 4/15、3/15。
    其他解釋
    reducer 直接套用 AOEP 規則，15/15 證明義務可被滿足，不證明實際系統能做到；讀取模型只有 3B–8B。
    直接測到嗎
    在九種手寫故障模式上直接測到差異。
    未測的邊界
    作者自己說沒有跑「給抽取式儲存加最小治理外殼」的消融，分不出是架構極限還是缺少欄位（§9.6）。
    評語
    部分支持 在試點規模內能區分；能否推廣到大模型與真實系統，作者與本站都認為尚未證明。
    D研究延伸：可否證的假說研究構想，不是已驗證的貢獻

    以下是研究構想，尚未被驗證。第一個是作者自己點名、但沒有跑的實驗。

    假說一：抽取式記憶缺的是欄位，還是架構本身就做不到？
    研究問題
    給 Mem0 類的抽取式儲存加上最小治理外殼（permission epoch、刪除帳本、信任層級、回滾帳本），義務分數能補回多少？
    可否證的假說
    若失敗是「欄位缺失」，加外殼後義務通過數會從 3–4/15 升到 12/15 以上；若仍低於 8/15，表示抽取式整併在寫入時就丟了治理需要的資訊，是架構限制。
    實驗情境
    沿用 AOEP-v0 的九種故障模式，每種擴充到 20 個實例；比較加與不加外殼。
    比較基線
    受治理 reducer（上界）、無記憶（下界）、原版 Mem0-style。
    控制變因
    同一事件串與探測問題；讀取模型做為一個因子（7B 與 32B 以上）；貪婪解碼。
    評估指標
    義務通過數、負向不變量通過數、逐項檢查的失敗分布。
    能分辨什麼
    「沒裝儀器」對「架構極限」，正是原文 §9.6 留下的問題；讀取模型因子還能看出更強的模型能否補位。
    可能失敗的條件
    故障實例太少時，差距會被個別題目主導；外殼欄位的設計若直接照搬 validator 規則，就會變成另一個 reducer。
    假說二：外部副作用的回滾到底有多少研究？
    研究問題
    rollback 的 27 篇合計了三種機制不同的回滾（附錄 A.6），其中最難的「外部副作用回滾」有多少？
    可否證的假說
    把 27 篇雙重編碼成內部狀態、工作流程、外部副作用三類後，外部副作用回滾少於 10 篇，而且其中有實測恢復成功率的少於 3 篇。
    實驗情境
    兩位編碼者獨立重新編碼 rollback 標籤的全部候選（含任一位曾標記的），並抽查語料中未標 rollback 的工作。
    比較基線
    原文的合併計數 27。
    控制變因
    編碼手冊事先寫好三類的判準；盲測、計算 κ。
    評估指標
    各子類篇數與 κ；有沒有報告恢復成功率或成本。
    能分辨什麼
    「回滾很少」是否主要反映最難的那一類。
    可能失敗的條件
    若子類界線本身模糊（例如工作流程補償是否算外部副作用），κ 會很低，需要先修訂判準。

    術語表

    Always-on agent
    行動依賴跨 session 累積之持久狀態的 agent；重點是持久，不是連續執行。
    持久狀態
    Persistent state：記憶，加上任務帳本、權限、憑證、承諾、出處與稽核紀錄、共享狀態、觸發條件，以及連到這些記錄的外部副作用。
    治理外殼
    Governance envelope：記錄 \(s\) 中除了值 \(v\) 以外的七個欄位。
    前向弧／回返弧
    observe→write→validate→organize→retrieve→act；update→forget→audit→rollback。
    權威單調性
    Authority monotonicity：只有目前未撤銷的權威能讓記錄影響行動，權威只縮不擴。
    Tombstone
    刪除標記：記錄被標為已刪除，並有義務把標記傳播到衍生副本。
    Permission epoch
    權威改變時遞增的整數，用來判斷行動當下有效的權限版本。
    Idempotency key
    冪等鍵：讓重播的重複操作被認出是同一個邏輯操作。
    Saga
    資料庫的長交易模式：以補償動作語意上撤銷已完成的步驟。
    受控複利
    Controlled compounding：能辨識、撤銷授權並回復造成退步的特定更新時，適應才算淨正面。
    AOEP
    Always-On Evaluation Protocol：以事件流與狀態快照評分狀態轉換的協議；v0 為試點。
