    01

    問題：找得到 ≠ 用對版本

    Figure 1 的兩個對照例子 原文 Figure 1

    A. 回想能力：使用者先說「我養了一隻貓叫 Smokey」，幾個 session 後說「想幫牠買刻名字縮寫的項圈」。系統 retrieve("cat") 取回 {cat = Smokey}，刻「S」，通過。

    B. 狀態追蹤能力：先說「我們有 1600 筆標註資料要分析，5 位標註員，總預算 $600」，系統記成三個互相牽動的衍生狀態（1600 pairs、5 annotators、$600 budget）。後來使用者說「其實改成 1200 筆」。再問「目前預算多少？」系統 retrieve("budget") 取回 {budget = $600} 並當成現況回答：狀態漂移（state drift）。

    原文沒有寫出改成 1200 筆後的正確預算，只說系統不但要知道最新筆數是 1200，還要看出這個改變對其他狀態的影響（§1）。

    你跟朋友說「我要買 3 顆蘋果，每顆 10 元，總共 30 元」。後來你改口「買 2 顆就好」。朋友記得你說過的每一句話，結帳時卻還是說「30 元」。他沒有忘記，他只是沒把改變算進去。這篇論文就是在抓這種錯。

    狀態漂移的定義（§3）：先前對話建立或更新過的事實、限制或依賴關係確實在組好的 context 裡，但 agent 依據的是過期或不完整的版本，而不是決策當下有效的那一版。

    這把「沒維護好狀態」和「沒取得資訊」分開。後者靠更好的檢索能修，前者不行：資料明明找到了，用錯的是版本。

    論文的四個貢獻（§1）：

    1. 把狀態追蹤定義成和回想（recall）不同的能力，並給出把漂移從其他錯誤中分離出來的標記程序（本頁 02、03）。
    2. StateMemBench：234 個多 session 情境，三個領域、長短兩種對話長度（04、05）。
    3. StateMem：以狀態為核心的記憶方法（06–10）。
    4. 證明狀態追蹤是可以單獨拆出來的一軸：同一套做法改成回答時的包裝器，對每個後端都有效，並用等長、等成本的對照組分離出「結構」本身的貢獻（11、12）。

    和對話狀態追蹤（DST）的差別（§2）：DST 規定狀態的表示法（領域本體上的 slot–value，或 schema-guided、open-vocabulary 的放寬版本），並直接評這個表示法。這篇不規定狀態長什麼樣，狀態就是「為了答對必須維護的東西」，評測純看行為。另外 DST 語料是合作式的，使用者目標在一段對話裡單調累積；StateMemBench 則刻意反覆修改事實和使用者或 agent 的決定。

    和既有記憶研究的關係：作者認為回想和狀態追蹤正交，就算檢索完美，系統仍要判斷取回的事實裡哪一個現在有效。Zep 對知識圖譜的邊加上有效時間區間、偵測到矛盾就讓舊邊失效，能追蹤單一事實的有效性；STALE 也處理狀態並傳播更新，但靠 LLM 裁決器在預先定義的 schema 上做，而 StateMem 用確定性、不呼叫 LLM 的依賴圖走訪。STALE 的衝突是隱性的（要常識推論才看得出來），StateMemBench 則明講衝突，把「維護」和「推論」分開（§2）。

    自我檢測
    為什麼更好的檢索修不好狀態漂移？

    定義上，漂移發生時正確的新值已經在 context 裡了。錯的是 agent 選了舊版本來用，問題出在「哪一版有效」的判斷，不在「找不找得到」。

    DST 和本文的「狀態」有哪兩點不同？

    一、DST 規定並直接評估狀態表示法，本文只看行為。二、DST 對話是合作、單調累積的，本文的情境會反覆推翻先前的事實與決定。

    自我檢測
    為什麼 Table 1 的漂移比例是「上限」而不是估計值？

    它是 LLM 判定者的標記；兩位人類標註員在同一批（刻意挑難的）案例上判出的漂移都更少（8.3%、25.0% 對 50.0%）。

    κ = 0.17 但一致率 91.6%，哪個比較能代表可靠度？

    這裡是一致率（以及 PABAK 0.83、AC1 0.91）。κ 在類別極度不平衡時會被機會校正壓低，原文也明說這是唯一 κ 失真的一格。

    κmode 接近 0 對研究設計有什麼影響？

    事後讀輸出無法可靠判斷漂移的機制，所以作者改成在情境生成時就指定機制，讓「是哪一種漂移」由建構決定，而不是靠判讀。

    完美檢索下的失敗 原文 §3.2、附錄 A.5

    5/21在一段問植物溫度的對話中順帶一句：「我也在照顧一個幫朋友小孩設的 1 加侖小缸，裡面有幾隻孔雀魚……」之後再也沒提。

    5/27整段都在談那個 20 加侖、取名「Amazonia」的缸，十幾輪討論魚、飼料、藻類、水草、沉木。

    5/30 提問「我現在總共有幾個缸，包括幫朋友小孩設的那個？」正確答案 3，agent 答 2。

    問題本身就點名了那個安靜的事實，agent 還是沒算進去。作者逐一排除其他解讀：不是檢索（全部都在 prompt）、不是理解（答了格式正確的數字）、不是格式、也不是合法更新（沒有任何缸被送走）。剩下的是「顯著性」不對稱：20 加侖缸有名字、被談了兩個 session；1 加侖缸只在別的問題裡出現一個子句。

    推理不是解藥（附錄 A.6）：同一批 50 題、同樣 prompt、完整歷史都在 context 裡，只切換 DeepSeek-V4-Flash 的推理軌跡。正確率從 84.0% 掉到 76.0%：救回 3 題、弄壞 7 題，精確 McNemar p = 0.34。用二項分布驗算：10 個不一致對中 ≤ 3 個偏向一邊的雙尾機率是 \(2 \times \frac{1+10+45+120}{1024} \approx 0.344\) 導讀補充：驗算。上面的魚缸案例正好是「off 對 → on 錯」：不開推理答 3，開了反而答 2。

    作者強調要看的是不對稱，而不是 −8 個百分點本身（方向不顯著）：推理讓失敗集合幾乎不動，而維護狀態的介入會動它。在同一題型和骨幹上，§6.4 的包裝器讓六個後端平均比各自單獨使用高 +20.9 個百分點。用 Table 6 的 LongMemEval／DeepSeek 欄驗算：\((15.0+20.0+31.7+30.0+25.0+3.4)/6 \approx 20.9\) 導讀補充：驗算。

    回到 00 的第二個猜測：打開推理能修好漂移嗎？

    在這組實驗裡不能。正確率從 84.0% 到 76.0%，差異不顯著（p = 0.34），失敗集合幾乎沒變。

    oracle 版保證所有證據都在 prompt 裡（召回 = 1.0），所以剩下的錯都不可能是檢索失敗偽裝的。

    04

    StateMemBench：用程式造陷阱

    核心設計 原文 §4.1

    失敗模式不是人工列分類表，而是機械地定義。每個情境先生成一個符號事件程式：一串有型別的狀態操作（宣告規則、更新值、有範圍的例外、承諾、撤回），作用在基礎、衍生、宣告三類狀態上。用確定性的評估器重播整個程式，得到探測題的正確答案。另外實作一組「偷懶讀者」策略，每一種模擬記憶系統的一種失敗：只信最近一次提到的值、只信最常出現的值、直接回報說過的數字而不重算、太急著丟掉先前錨定的決定。只要有一個以上的策略和完整重播的答案不同，就是一個陷阱；不同的那些策略構成這個情境的失敗模式簽章。

    封閉選項池評分（§4.3）：生成情境時就建好 3–4 個可能答案：gold、被瞄準的偷懶策略算出的漂移答案、相關的中性干擾項。作答時不顯示選項。所以每個答案可以歸入：答對、漂移、其他選項、池外（沒答出可辨識的選項）。一個確定性的詞界比對器處理 28% 只點名唯一選項的答案，與判定模型在這些答案上一致 94.1%；其餘交給判定模型對應（附錄 C）。

    StateMem：寫入、更新、回答三階段

    \[ u = (\mathit{id},\ \mathit{content},\ \mathit{priority},\ \mathit{source},\ \mathit{deps}),\qquad \mathit{priority} \in \{\text{hard}, \text{soft}\} \] \[ G = (U, E),\quad (u_i, u_j) \in E \iff u_i \text{ depends on } u_j,\qquad \text{Rechecker cost} = O(|E|) \]
    \(u\)
    狀態單元（state unit），存在跨 session 的 StateStore 裡。
    content
    自由格式的內容，例如「實領薪水 $6000」。
    priority
    hard：已驗證的事實、有約束力的承諾、未完成的義務；soft：偏好、可以讓步的東西（附錄 E.1 提示詞）。
    source
    來源的輪次與說話者。
    deps
    有型別的連結：derived_from（值是從另一個單元算出來的）或 coupled_with（有效性取決於另一個單元的狀態，例如「Netflix 自動扣款綁在卡 3」依賴「卡 3 是否停用」）。
    \(G\)
    依賴圖；邊 \((u_i,u_j)\) 表示 \(u_i\) 依賴 \(u_j\)。

    AI 有一本筆記本，每一行都寫「這是什麼」「重不重要」「誰說的」「跟哪幾行有關」。有人改口時，舊的那行劃掉但不撕掉；跟它有關的行旁邊貼上「要重算」的便利貼。要回答問題時，只看沒劃掉的行，貼了便利貼的就重新算一次。

    1. 寫入（§5.1）：TurnEncoder 每一輪對話呼叫一次 LLM，把這一輪解析成零到多個狀態單元，並把目前所有有效單元的精簡版當 context。它也可以把既有單元標記為「可能被取代」並主動提出替代版本。有日期的資料，單元會蓋上該輪日期。
    2. 更新（§5.2）：兩個動作。一、StateStore 套用標記的取代：被取代的單元狀態改為 superseded，替代版本以 active 新增。二、確定性的 Rechecker 走訪依賴圖：凡是有邊連到「狀態剛改變的單元」的 \(u_i\)，標成 needs_recheck。這一步是 \(O(|E|)\)，不呼叫 LLM。
    3. 回答（§5.3）：StateStore 確定性地把所有 active 單元（包括 needs_recheck 的）組成結構化區塊 \(S\)，依優先度與來源分組，被標記的單元旁邊註明觸發原因。再用一次 LLM 呼叫，輸入 \(S\)、問題和「重算指引」來回答。

    被取代的單元留在庫裡供稽核，但不再送進回答階段；needs_recheck 的單元仍然有效，只是帶著旗標。

    分工：確定性的層決定哪些單元有效、哪些可能過期；LLM 只負責在這些旗標下重算答案（§5.3）。這和 STALE 的 CUPMem 用 LLM 裁決器判斷失效不同。

    Rechecker 只走一跳：正文寫的是「有邊連到狀態剛改變的單元」。多跳的連鎖由回答時的重算指引處理：「如果結果又餵給另一個 NEEDS RECHECK 單元，就用剛算出的值重算那一個，沿著鏈依序傳播後再回答」（附錄 E.3）。這是本頁對兩段文字的合讀 導讀補充。

    正文和提示詞的欄位不完全一樣：正文的單元是五元組；附錄 E.1 的輸出格式還有 type、scope、source_type（user／action／tool_result）和 triggers（date_passed、entity_closed、supersession_announced、cascade）。PolicyEncoder 每個情境只跑一次，把政策文件拆成同樣格式的單元；在評測過的資料中只有 τ² 真的有政策文件（附錄 E.2）。

    成本：每一輪一次編碼呼叫，一個情境約 165–600 次（附錄 H）。作者在限制段落承認這比單純 long-context 耗費多得多。

    回答時注入的狀態區塊格式 原文附錄 E.3 
    ## BINDING -- THIS CONVERSATION
- [<type>] <unit content>
## BINDING -- POLICY RULES
- [<type>] <unit content>
## PREFERENCES (yield if necessary)
- [<type>] <unit content>
## ! NEEDS RECHECK -- may be stale due to recent events
- [<type>] <unit content>
  -> trigger: <reason>

    重算指引的重點：標為 NEEDS RECHECK 的單元是過期的，不要用它的數字；取它寫明的推導式（例如 X = A × 2），代入目前 active 狀態中每個輸入的值重算；只重算問題路徑上的單元；硬限制（醫療、範圍限定）優先於最近的軟偏好。

    自我檢測
    derived_from 和 coupled_with 差在哪？

    前者是「值」從別的單元算出來（輸入變了要重算）；後者是「有效性」取決於別的單元的狀態（對方關閉或被取代，這條要重新評估）。

    superseded 和 needs_recheck 的單元，哪個會送進回答階段？

    只有 needs_recheck 的會，而且帶著旗標。superseded 的留著供稽核，但被排除。

    更新階段為什麼不需要 LLM？

    依賴關係在寫入時就記錄下來了，更新只是沿邊走訪、改狀態欄位，是 \(O(|E|)\) 的圖演算法。

    以下是研究構想，尚未被驗證。

    假說一：持久儲存庫什麼時候才必要？
    研究問題
    包裝器在同一批題目上勝過 StateMem 本身（Qwen：0.283 對 ≥ 0.567）。對話放不進 context 時，StateMem 的儲存庫是否會反超？
    可否證的假說
    當對話長度超過回答模型可用的 context（或被截斷到固定預算），包裝器的準確率下降幅度會大於 StateMem；交叉點出現在 context 預算小於對話長度的某個比例。
    實驗情境
    以 Set B 情境為底，插入干擾 session 放大到 2、4、8 倍，或把 context 截到 4k、8k、16k；比較各方法。
    比較基線
    StateMem、包裝器、long-context、Dense 檢索加包裝器。
    控制變因
    同一骨幹、溫度 0、同一評審；每個設定 3 次執行。
    評估指標
    gold 比例、drift-rate、池外比例、每題總 tokens。
    能分辨什麼
    「回答時解析就夠了」對「需要持久化的狀態」。
    可能失敗的條件
    若 TurnEncoder 的錯誤也隨對話長度累積，StateMem 會一起退化，看不出交叉點。
    假說二：助理回想的掉分來自 TurnEncoder 的偏重嗎？
    研究問題
    LongMemEval 單 session 助理回想題掉約 40 個百分點，是不是因為 TurnEncoder 沒把助理說過的內容存成單元？
    可否證的假說
    在 TurnEncoder 提示詞加入「助理提供的內容與承諾」這類單元後，助理回想題至少收回一半差距，而 StateMemBench 分數不下降。
    實驗情境
    只改 TurnEncoder 提示詞一處，其他不變；跑 LongMemEval 全集與 StateMemBench。
    比較基線
    原版 StateMem、long-context。
    控制變因
    同一骨幹、k、評審、溫度。
    評估指標
    LongMemEval 分題型準確率（特別是 56 題 SS-assistant）、StateMemBench gold 比例與 salience 類分數、狀態區塊長度。
    能分辨什麼
    掉分是「沒存」造成，還是「存了但回答時沒用上」。
    可能失敗的條件
    狀態區塊變長可能讓 salience 類更差，需要同時觀察。

    術語表

    狀態追蹤
    State tracking：在長期互動中維護事實、規則與衍生量目前有效的值。
    狀態漂移
    State drift：正確的新值在 context 裡，agent 卻依據過期或不完整的版本行動。
    回想
    Recall：取回相關事實的能力。本文認為它和狀態追蹤正交。
    符號事件程式
    Symbolic event program：一串有型別的狀態操作，重播後得到 gold。
    偷懶讀者策略
    Lazy reader policies：模擬記憶系統失敗的小型啟發式，例如只信最新提及、不重算衍生值。
    封閉選項池
    Closed pool：生成時就建好的 3–4 個候選答案（gold、漂移、中性干擾），作答時不顯示。
    池外
    Off-pool：答案無法對應到任何選項。
    drift-rate
    選了漂移目標的答案數 ÷ 全部題數。
    狀態單元
    State unit：StateMem 的記憶基本單位 (id, content, priority, source, deps)。
    superseded / needs_recheck
    被取代（保留稽核、不送進回答）／需重新檢查（仍有效但帶旗標）。
    Rechecker
    確定性的依賴圖走訪，把依賴剛改變單元的單元標為 needs_recheck。
    StateMemWrapper (SMW)
    把狀態解決原則寫進單次回答提示詞的包裝器：trace 加上 resolve。
    wrapper-ctrl
    等長、等成本但沒有結構的對照提示詞。
    PABAK
    Prevalence-adjusted bias-adjusted kappa，\(2P_a - 1\)，類別不平衡時比 κ 穩定。
    McNemar 檢定
    比較兩個條件在同一批題目上的配對對錯，只看不一致的題對。
    DST
    Dialogue state tracking：任務型對話中以 slot–value 追蹤使用者目標的傳統任務。
